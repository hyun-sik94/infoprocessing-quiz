CLAUDE.md

IT 자격증 스마트 CBT: 정보처리기사(필기·실기)와 네트워크관리사 2급(필기) 기출문제 풀이 웹앱.

  1. 승인 없이 코드를 수정하지 않는다. 먼저 무엇을 왜 어떻게 바꿀지 제안하고, 사용자가 승인한 범위만 수정한다.
    • "확인해줘", "검토해줘", "테스트해줘"는 수정 승인이 아니다. 결과와 수정안만 보고한다.
    • 승인받은 범위 밖의 리팩터링, 포맷 정리, 주석 정리, 이름 변경을 끼워 넣지 않는다.
  2. 승인 없이 커밋·푸시·브랜치 작업을 하지 않는다. git commit, git push, git reset, git checkout -- ., git stash, 리베이스, 태그 생성 모두 해당한다. 사용자가 요청하면 커밋 메시지를 먼저 보여 준다.
    • push는 곧 운영 배포다. 서버가 재시작되어 풀이 중이던 사용자의 세션이 끊긴다.
  3. 데이터 파일(data/**/*.json)은 코드보다 더 신중히 다룬다. 승인 없이 수정·재정렬·재포맷하지 않는다. 수정할 때는 바뀐 문항 id와 필드를 목록으로 보고한다.
  4. 파일 삭제, 패키지 설치·삭제, feedback.db 변경은 승인 후에만 한다.
  5. 운영 서버나 실데이터에 쓰기 요청을 보내지 않는다. 테스트 중에도 /api/feedback(제보하기)은 전송하지 않는다.
  6. 사용자 브라우저에 저장된 기록을 바꾸거나 지우는 코드를 넣지 않는다. 즐겨찾기·이력·진행도는 읽기만 하고, 새 기능은 기존 기록 위에 덧붙이는 방식으로 만든다(2026-11-13 사용자 요청).
  7. 모르는 것은 추측하지 말고 확인하거나 질문한다. 실행하지 않은 검증을 했다고 말하지 않는다.
  8. 사용자와는 한국어로 대화한다.

  • 순서: 관련 파일 읽기 → 원인·영향 범위 설명 → 수정안 제시 → 승인 → 수정 → 검증 → 결과 보고.
  • 수정 보고에는 바뀐 파일, 함수, 이유, 검증 방법, 남은 위험을 적는다.
  • 한 번에 하나의 문제만 고친다. 여러 결함은 우선순위를 매겨 하나씩 승인받는다.
  • 프런트 파일(app.js, style.css)을 수정하면 index.html의 캐시 버전을 같이 올릴지 사용자에게 묻는다. 안 올리면 브라우저가 옛 파일을 쓴다.
  • "화면이 그대로다", "수정이 안 됐다"는 제보는 먼저 캐시를 의심한다. 현재 코드와 수정 전 코드(git show 커밋:경로)로 각각 재현해서 어느 쪽 증상인지 가린다.

도구 사용 시 주의 (실제로 사고가 난 항목)

  • UTF-8 파일을 PowerShell의 Get-Content/Set-Content로 고치지 않는다. 시스템 인코딩(cp949)으로 읽고 저장해서 한글이 전부 깨진다(2026-11-10 index.html 사고). 파일 수정은 편집 도구나, 바이트/UTF-8 명시 방식(python -X utf8)을 쓴다. 깨졌다면 git show HEAD:경로로 복원한다.
  • Bash 도구의 명령 문자열 안 백슬래시(\\, \n)는 줄어들어 전달된다. 이스케이프가 들어간 패치 스크립트는 파일로 만들어 실행한다.
  • 줄바꿈: 작업 트리의 app.js, style.css, server.js는 CRLF, index.html과 net2.controller.js, lib/quiz-utils.js는 LF다(git core.autocrlf=true). 파일의 기존 줄바꿈 형식을 유지하고 혼재시키지 않는다.
  • BOM을 추가하지 않는다. 수정 후 U+FFFD가 없는지 확인한다.
  • 3000 포트는 사용자가 쓴다. 테스트 서버는 다른 포트(PORT=3001)로 띄우고, 끝나면 반드시 종료한다. 사용자가 띄운 프로세스는 종료하지 않는다(2026-11-10 테스트 서버가 3000을 점유해 사용자의 npm start가 실패했다).

npm install        # express, cors, better-sqlite3
node server.js     # 기본 포트 3000 (PORT 환경변수로 변경)
  • 접속: http://localhost:3000
  • 관리자 API는 환경변수 ADMIN_PASSWORD를 설정해야 켜진다. 미설정이면 항상 401이다. 예: PowerShell $env:ADMIN_PASSWORD="새비밀번호"; npm start
  • 이미 3000 포트를 쓰는 프로세스가 있으면 EADDRINUSE 오류로 서버가 바로 종료된다. 다른 포트($env:PORT=3001)로 켜거나 기존 프로세스를 먼저 종료한다.
  • 세션은 서버 메모리(Map)에 저장된다. 서버를 재시작하면 진행 중인 시험의 정답 확인과 제출이 400 오류가 된다. (브라우저에 저장된 이어풀기 진행도는 그대로 남는다.)
  • 배포: .github/workflows/deploy.yml. main에 push하면 운영 서버에서 git pull → npm install --omit=dev → pm2 reload quiz-app을 실행한다. 배포 성공 여부는 GitHub Actions 실행 기록으로 확인한다.
  • 정적 파일은 express.static으로 서빙하고 index.html에 캐시 방지 헤더가 없다. 배포 후에도 브라우저가 옛 index.html을 쓰면 옛 app.js·style.css가 그대로 보인다.

API

두 서버가 같은 모양이다: GET /rounds, POST /new, POST /check-answer, POST /submit, GET /search.
/new는 클라이언트에 answer와 desc를 빼고 보낸다. 정답은 /check-answer와 /submit으로만 나간다. 이 원칙을 깨지 않는다.

  • POST /new 본문: year, examType, bookmarkIds, subject, targetQuestionId, resumeIds
    • 분기 우선순위: targetQuestionId(단일) → resumeIds(이어풀기) → bookmarkIds → year==='sequential' → subject → year==='cbt'|'all'(랜덤) → 그 외는 회차/연도 매칭(source includes).
    • bookmarkIds는 배열을 기대하지만 {ids:[...]} 객체도 받아준다(normalizeBookmarkIds).
    • resumeIds: 정수 배열(최대 2000개)이고 year가 sequential/subject/bookmark/target이 아닐 때만 인정한다. 저장된 id 순서 그대로 세션을 복원한다. 회차 풀이는 시작마다 문항이 섞이는데(네트워크관리사) 이어풀기에서 순서가 바뀌면 안 되기 때문이다.
    • 응답 문항에는 type이 항상 들어간다(실기 데이터에는 type이 없어 서버가 practical로 보강).
    • 랜덤(cbt/all)은 문제+보기가 같은 중복 문항을 제거한 뒤 뽑는다(dedupeQuestions).
    • 보기 순서는 섞지 않는다. 문항 순서만 섞는다.
  • POST /submit 응답: score, total, isPassed, isGwarak, gwarakApplied, gwarakSubjects, reviewData. reviewData에는 type, subject, userAnswer, realAnswer, earnedScore, maxScore가 있다. DB에는 아무것도 쓰지 않는다.
  • GET /search: 결과에 type을 보강해서 돌려준다(검색 결과에서 즐겨찾기할 때 필요).
  • 세션에는 examLike(랜덤·회차 풀이 여부)가 저장된다. 과락 판정에 쓴다.

공통

  • 파일은 UTF-8, 유효한 JSON 배열이어야 한다(끝 쉼표 금지). 저장 후 파싱 검증을 한다.
  • id는 함부로 바꾸지 않는다. 사용자 브라우저의 즐겨찾기, 풀이 이력(solvedIds), 분석 탭의 "문제풀기", 오답 노트, 순차풀이·회차 풀이 저장본이 id나 순서에 의존한다. (2026-11-10 네트워크관리사 id를 1~1150으로 재부여해서 이전에 저장된 기록이 다른 문항을 가리킬 수 있게 됐다.)
  • text도 함부로 바꾸지 않는다. 즐겨찾기는 text로 식별하고, 오답 노트와 My 탭 정답 보완은 저장된 text가 현재 데이터와 같은지로 같은 문제인지 판단한다. 문제 text를 바꾸면 그 문제의 기존 즐겨찾기·오답 노트 연결이 끊긴다. 텍스트 수정은 영향 범위를 함께 보고한다.
  • source로 회차를 매칭한다(includes 방식). 표기 형식을 바꾸지 않는다.
  • 데이터를 바꾼 뒤 확인할 것: JSON 파싱, id 중복·연속성, 회차별 문항 수, answer 범위(1~4), desc의 정답 번호 일치, 해당 문항의 화면 렌더링(모바일 390px·데스크톱, 라이트/다크).

정처기 필기 data/written.json

  • 키: id, type, source, subject, text, view, choices, answer, desc
  • id 형식은 YYYYRRNN(회차당 100문항이라 100번째는 YYYYRRNNN, 예: 20200101 = 2020년 1회 1번, 202602100 = 2026년 2회 100번). source 예: 2020년 1회 필기 기출
  • subject는 1과목: 소프트웨어 설계 ~ 5과목: 정보시스템 구축관리, 회차당 과목별 20문항. 분석 탭은 이 subject를 쓴다.
  • desc는 한 줄 설명 형식이며 [오답 풀이] 섹션이 없다(네트워크관리사와 다름).

정처기 실기 data/practical.json

  • 키: id, source, text, view, answer, desc (+ 다중 입력 문항은 inputCount)
  • type 필드가 없다. 서버가 응답에서 practical로 보강하지만, 데이터를 직접 읽는 코드를 만들 때는 주의한다.
  • 복수 정답은 ,로 구분한다. |는 대체 표기로 지원한다(아래 채점 규칙).
  • id 107은 비어 있다.

네트워크관리사 2급 필기 data/net2/written.json

  • 키 순서: id, source, subject, type, text, view, choices, answer, desc
  • id는 1~1150, 2021년 1회 → 2026년 4회 순서. source 예: 2026년 1회 기출. 23개 회차, 회차당 50문항. 2023년 4회는 없다.
  • subject는 TCP/IP, 네트워크 일반, NOS, 네트워크 운용기기 4개.
  • text: 질문 + \n\n + 이미지에서 옮긴 지문. 앱은 첫 줄을 굵은 질문, 나머지를 지문 카드로 그린다. 시나리오형 문제는 질문을 첫 줄로 올리고 지문은 문장 단위로 줄바꿈한다. "이때…", "해당…"처럼 앞 지문을 가리키는 질문은 원래 순서(지문 → 질문)를 유지한다. 불릿은 - .

진행도와 이어풀기

  • 회차·랜덤 진행도(*_회차풀이_중간저장): 객체 { "<mode>|<year>": { year, mode, ids, currentQuizIndex, savedUserAnswers, remainingTimeSeconds, answered, total, savedAt } }.
    • 저장 시점: 문항 렌더링, 답안 선택·입력, 타이머 10초마다, 화면 가려짐·페이지 이탈(visibilitychange, pagehide). 아무것도 안 풀고 1번이면 저장하지 않는다. 제출하면 삭제한다.
    • 이어풀기는 triggerNewQuizSession(year, …, 'resume'). 서버가 resumeIds를 모르는 옛 버전이어도 클라이언트가 저장된 순서대로 다시 정렬한다. 문항 구성이 달라졌으면 저장본을 버리고 처음부터 시작한다.
  • "이어서 풀기" 카드: 첫 화면과 각 대시보드 맨 위. 저장된 풀이로 확인창 없이 바로 이동하고, ✕로 삭제한다(listSavedSessions, buildResumeCardHtml, resumeSavedSession). 회차 목록에는 · 진행 중 40/50이 붙는다.

풀이 화면

  • 세션 시작: triggerNewQuizSession(year, ids, subject, targetId, resumeMode, opts). opts.label은 이력에 남길 제목(서버 라벨 대신), opts.expected는 {id: text}로 서버가 돌려준 문항이 저장된 문제와 같은지 검사할 때 쓴다(오답 노트).

My 탭 (즐겨찾기)

  • 문제, 지문(view), 필기는 보기 4개(정답 보기 강조), 정답, 해설을 보여 준다(renderMyBookmarksTab).

분석 탭

  • 오답 노트: 맨 위 카드에서 "모든 문제" 또는 회차(source)를 골라 틀린 문제만 다시 푼다(buildWrongNoteData, buildWrongNoteCardHtml, startWrongNoteQuiz).

    • 같은 문제 판단: text + view + 정렬한 보기가 같으면 한 문항(wrongNoteKey). 재출제 문제는 한 번만 세고, 푼 회차마다 회차별 목록에 나타난다.
    • 이력의 id가 현재 데이터에서 다른 문제이면 그 문항만 빼고 시작하며, 빠진 개수를 알린다.

렌더링과 레이아웃

  • 화면 렌더링은 innerHTML 문자열 조립 방식이다. 사용자 입력이나 데이터 문자열을 넣을 때는 escapeHtml()을 쓴다. 입력칸 value와 source도 이스케이프한다.
  • formatViewHtml: 코드 패턴은 코드 박스, |가 있는 줄은 표로 바꾼다. 단, 파이프가 있어도 명령어·터미널·스크립트로 판정되면(looksLikeCommandText) 표 대신 code-flow-box term(줄바꿈·들여쓰기 유지, 가로 스크롤)으로 그린다. 들여쓴 블록(불릿 목록 제외)도 같은 박스다. 데이터를 고칠 때 이 렌더링 결과를 같이 확인한다.
  • 레이아웃: 모바일 기본(최대 430px), 769px 이상은 2단 레이아웃(최대 960px). html, body에 width: 100%가 있어야 한다(없으면 내용물 폭에 따라 앱 폭이 달라진다). flex 안의 입력칸은 min-width: 0이어야 좁은 화면에서 버튼이 카드 밖으로 밀리지 않는다. 라이트/다크 테마 모두 확인한다.
  • 한 화면 안에서 요소가 부모 카드 영역을 벗어나는지도 확인한다. 화면(viewport) 밖으로 나가는지만 보면 overflow: hidden인 앱 영역 안에서의 이탈을 놓친다.
  • 새로 만드는 입력칸·선택 상자는 글자 크기를 16px 이상으로 한다(iOS 사파리 자동 확대 방지).

  • 사용자 기록에 의존하는 기능(오답 노트, 이력, 즐겨찾기)은 가짜 기록을 localStorage에 넣어 검증하고, 기능 실행 전후의 저장 내용을 비교해 기존 기록이 그대로인지 확인한다.
  • 데이터 변경 후에는 "데이터 규칙 > 공통"의 확인 항목을 점검한다.

검증 방법에서 주의할 점:

  • 전수 검사는 UI 클릭이 아니라 스크립트로 한다. 전 회차 API 채점(전부 정답/오답/미입력/60점/59점 경계, 정답 유출 없음), 전 문항 렌더링 스캔(이상 문자열, 보기 4개, 빈 view, 오버플로), 앱 폭 스캔을 쓴다.
  • 스크롤을 보는 테스트에서 Playwright click()/tap()을 쓰지 않는다. 화면 밖 요소를 누르기 전에 스스로 스크롤해서 앱의 스크롤 동작과 구분되지 않는다. 스크롤을 건드리지 않는 element.click()(JS)로 검증한다.
  • 모바일 에뮬레이션(isMobile)은 스크롤바가 없다. 사용자가 데스크톱 브라우저 창을 줄이거나 확대(125% 등)한 경우는 isMobile: false로 폭을 줄여 따로 본다.
  • 수정 전 코드와의 비교: git show HEAD:경로로 수정 전 파일을 라우트로 주입해 같은 시나리오를 돌리면 "고쳐졌는지"를 증명할 수 있다.
  • 한글 포함 테스트 스크립트는 파일로 만들어 UTF-8로 실행한다(python -X utf8, PYTHONIOENCODING=utf-8).
  • 알려진 테스트 한계: 정답 확인 스크롤 검사(E6)와 과락 배너 문자열 검사(QW-13)는 검사 방식 때문에 실패로 나온다. 앱 결함이 아니다.
